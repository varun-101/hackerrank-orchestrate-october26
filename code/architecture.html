Ghost Data Still Exists

A hand-drawn tour of our deletion-audit agent: the program that checks whether a company really deleted someone's personal data, or only said it did.

Written for a beginner developer. Every box is a real piece of code in code/; every tricky word is explained in the glossary at the bottom.

TL;DR
We read every piece of evidence the company kept (databases, logs, PDFs, screenshots), figure out who the person is, travel back in time to the audit moment, and check each copy of their data against the deletion rules. Then we write a step-by-step "here is what is left and how to fix it" plan.

1. The problem in one picture

Deleting a user is not one action. Their data has been copied all over the place. The deletion workflow might happily report COMPLETE while copies (the "ghost data") are still sitting around, and some background jobs can even bring deleted data back.

🙋 A person asks:
"Please delete my account and my data."
a row in deletion_requests.csv
workflow runs
✅ The system claims:
reported_status = COMPLETE
this is only a claim, not proof
but...
👻 a reporting replica still has the row
👻 a log still shows the email
👻 an old export file is still there
🔄 a nightly sync or backup restore can copy it back

Our job, part 1

Decide if the request really asks for deletion. "Send me a copy of my data" or "stop marketing emails" is not deletion → answer NOT_APPLICABLE.

Our job, part 2

If it is a deletion, find every copy of that person's data as it was at the audit time, and judge each copy with the company's deletion rules.

Our job, part 3

Answer COMPLETE (with proof) or INCOMPLETE (with what is left, a safe fix plan, and the checks to run afterwards).

3. The pipeline, station by station

Each request goes through these stations in order. Most of them are plain, deterministic Python (same input → same output, every time). The colour tells you how a station makes its decision:

plain code (deterministic) uses an LLM (AI model) inference (a best guess, clearly tagged) hard rule applied everywhere
1

Load and normalize all evidence

code/evidence.py

"Pour every drawer onto one table, and label each item."

Evidence comes in many formats. We turn every record, log line, SQL row, PDF line and screenshot fact into the same shape, called an observation: which system, which resource (e.g. account_4857), which identifiers (emails, phones, hashes), what fields, what time, and the exact source text so we can cite it later.

"Nothing found" is also an observation. An empty table in a database snapshot, or a 404 from a profile lookup, proves the record is absent, but only for what that file actually covers.

Show how each format is read 
JSON  -> walk nested objects, carry parent context down to each record
LOG   -> group lines by trace_id; a lookup line + its result line = 1 observation
SQL   -> load into an in-memory SQLite database; keep primary and every replica table apart
PDF   -> extract text with pypdf (no AI needed)
TXT   -> parse the row format
PNG   -> facts read by the LLM, then checked by a human (see "AI usage")
2

Read the activity stream

code/activity.py

"Read the company diary, but don't believe everything it brags about."

system_activity.csv is one big diary of what every service did: delete jobs, syncs, exports, backups, restores. We sort it by event_time (not by ID, a few rows are out of order) and pull extra facts out of the free-text details column, such as "repopulated downstream resource X" or "Target resource: Y".

A row saying reported_result = SUCCESS is a claim. It is never treated as proof that data is gone.

3

Intent: is this really a deletion request?

code/llm_tasks.py (LLM) + code/intent.py (keyword rules)

"Read the letter and decide what the person actually wants."

Requests are written in 6 languages and can be tricky: "remove me from marketing lists only" is not account deletion, but "please confirm my earlier deletion really happened" is a deletion audit. An LLM is the main judge; frozen keyword rules double-check it. If the answer is not deletion, the case ends here with NOT_APPLICABLE and [].

If the model says UNSURE, the whole run stops before writing any answers, so a human can look. We never guess.

4

Identity: who is this person, really?

code/identity.py

"One person, many name tags."

The request email might be the person's current email or an old one. We map it to a stable user_id, then collect every identifier they have had: current and historical emails, phones and email hashes from user_audit_log.csv. Old systems often still hold the old email.

We only match exact identifiers. A look-alike email (jon.doe vs john.doe) is a decoy, not a match.

5

The cutoff: travel back to audit_at

pipeline.eligible(), used in every stage

"Answer as if you were standing at that exact moment. No peeking at the future."

Each request has an audit_at time. Only evidence captured at or before it counts: files, record times, activity rows and identity changes. A file captured one day later is ignored, even if it would make the answer easier. See the time machine diagram.

6

Linking: which records belong to this person?

pipeline.request_links() + code/inference.py

"Connect the dots, and say how sure you are about each dot."

Every link between a resource and the person gets a label: proven (evidence names both), lookup (a search with the person's email returned that resource), or inferred (no file names them together, so we make a careful, scored guess). Details in the linking deep dive.

If one person filed several requests, each link goes to the request whose time window contains it.

7

State: what does each copy look like right now?

pipeline.state_entries(), latest_per_copy()

"For each copy, the newest photo wins."

A record can live in several physical copies: the primary database, regional replicas, a reporting replica, a failover replica. For each copy separately, the latest eligible observation decides its state: still there with PII, cleaned, or absent. A clean primary never hides a dirty replica.

8

Policy: what should happen to it?

code/policy.py + dataset/deletion_rules.csv

"Look up the rule book for this kind of record."

Each record is put in a data category by its content, not by which service holds it (an analytics contact lookup must be deleted, an analytics profile only anonymized). The category gives the required action: DELETE, REDACT, ANONYMIZE, RETAIN, or keep a tombstone. See the rule book.

9

Steps and citations

pipeline.build_steps(), pipeline.pick()

"Write the report, and point to the proof for every claim."

Compare "what it looks like" (stage 7) with "what it should look like" (stage 8). Every violation becomes a finding, then a remediation (fix), then a verification (check). Findings cite the file or activity row that proves them. For a COMPLETE case, each check cites the evidence that proves the good state.

How we pick which file to cite 
1. a file that names the resource itself
2. the file that already holds this case's other cited observations
3. a file whose scope covers primary AND replicas
4. otherwise: latest capture time, then file_id
10

Order, serialize and validate

code/output.py

"Tidy the report so a robot grader can read it."

Steps are sorted by phase (FINDING, REMEDIATION, VERIFICATION), then the official operation order, then system_id, then resource_id, and numbered from 1. JSON is written deterministically. A validator checks every row: allowed operations only, consecutive numbers, empty evidence_id on future work.

4c. Linking records: proven, lookup, inferred

✅ Proven

A file (or an activity row's details) contains both the person's identifier and the resource.
e.g. a JSON record with email and resource_id side by side.

🔍 Lookup

A search was made with the person's email, and the completed result in the same log trace returned the resource.
A resource ID that only appears in the request line does not count.

🧠 Inferred

Nothing names them together. A deleted account may survive only as "Deletion worker submitted primary profile account_4857". We guess which request it belongs to, carefully.

How the inferred guess works: a fair matchmaking game

Picture a dating app. On one side are requests that still need a resource; on the other are "orphan" activity rows (a delete or anonymize job that names a resource but no person). Each possible pair gets a cost. Lower = better fit. Each row can go to at most one request. A solver (scipy.optimize.linear_sum_assignment, the "Hungarian algorithm") finds the pairing with the lowest total cost.

⏰ Time
The row should happen close to the request's reported_at. Each hour outside the expected window adds 2.0.
🤝 Status agrees
Account rows: COMPLETE should pair with SUCCESS, NOT_STARTED with FAILED. A mismatch adds 0.5.
↔️ Same side
Analytics rows: should fall on the same side of reported_at as the request's other proven jobs. A conflict adds 1.5.
Request Areported 10:00, COMPLETE
row X ✔09:20, SUCCESS · cost 0.00 row Y13:30, FAILED · cost 6.50 no matchcost 1.00
Request Breported 13:00, NOT_STARTED
row Xtaken by A row Y ✔13:30, FAILED · cost 0.00 no matchcost 1.00
Request Creported 18:00, COMPLETE
row Z15:10, SUCCESS · cost 2.67 no match ✔cost 1.00

Safety valves: "no match" always costs 1.00, so a weak candidate is never forced. Equal costs are broken by case number, then activity time, so shuffling the input changes nothing. Close calls are flagged ambiguous. The whole game is solved separately for each audit_at, using only rows visible at that moment. Every inferred link is tagged in the trace with its signals. (Numbers in this drawing are illustrative.)

4d. The rule book (deletion_rules.csv)

🗑️ DELETE

remove the whole record
  • user profile
  • secondary identifier
  • search index entry
  • cache entry
  • support attachment (only the subject's)
  • user export
  • marketing profile

✂️ REDACT

keep the record, cut out the PII
  • support message with shared context
  • email delivery log
  • account tombstone: keep only user_id, remove name, email, phone, email hash

🎭 ANONYMIZE

keep it, but unlink it from the person forever
  • analytics profile
  • product telemetry

🔒 RETAIN

must stay, by law or policy
  • security audit log (in retention)
  • legal hold record
  • backup archive, but block restore so it cannot bring data back

Deleting something that must be retained is also a mistake. "Delete everything" is never the right answer.

6. Where the AI is used (and where it is not)

We use an LLM in exactly two places, where plain code would be fragile. Everything else is ordinary Python that you can read and debug line by line.

💬 Request intent

Many languages, negations ("marketing lists only"), and "verify my earlier deletion" requests. The LLM decides; keyword rules cross-check; disagreements go to a human, and fixes go into the prompt or the rules, never into stored per-case answers.

🖼️ The 11 screenshots

Facts that exist only as pixels. The LLM reads them once, a human checks each fact against the image, and the approved facts are saved in code/cache/reviewed_facts.md, locked to the image's SHA-256 fingerprint. If the image changes, the run stops until it is re-checked.

💾 Cache

Every model answer is saved in code/cache/llm_cache.json, keyed by a hash of model + prompt + version (+ image). A second run makes zero network calls, so a judge can run it without signing in.

⚡ Parallel calls

Unique requests are de-duplicated, then sent through a pool of 8 worker threads with timeouts and up to 3 attempts. Results are keyed by cache key, so finishing order never changes the output.

🔑 Sign-in

code/llm_auth.py signs in with ChatGPT once and passes a short-lived token to the run through an environment variable. No secret is ever written to the repo or the logs.

9. Glossary for beginners

PII
Personally Identifiable Information: anything that points to a person, like a name, email or phone number.
Ghost data
Copies of personal data that survive after a deletion was reported as done.
Primary vs replica
The primary is the main database. Replicas are automatic copies (for speed, reports or failover). Deleting from one does not always delete from the others.
Backup and restore
A backup is a saved snapshot. Restoring it puts old data back, including data that was deleted since.
Data flow / sync
A background job that copies data from one system to another. If it keeps running, deleted data can reappear.
Tombstone
A tiny leftover record that says "this account existed and was deleted". It keeps only the internal user_id so other records still make sense.
Delete / Redact / Anonymize / Retain
Remove it all / blank out the identifying fields / make it impossible to link back to the person / keep it as is.
Cutoff (audit_at)
The moment we answer for. Anything that happened later is invisible to that case.
Observation
One normalized fact from one evidence file: "at time T, system S had resource R with these fields", or "had nothing".
Deterministic
Same input always gives the same output. No randomness, so results are repeatable and testable.
LLM
Large Language Model: an AI that reads and writes text (and here, reads screenshots). Powerful but not always right, so we fence it in.
Prompt
The instructions we send to the LLM. Ours live in code/llm_tasks.py and are versioned.
Cache
A saved copy of an earlier answer, so we don't have to ask again (faster, cheaper, repeatable).
Hash
A fixed-length fingerprint of some data. Same input, same hash. We use it to spot emails stored as hashes and to detect changed images.
Assignment problem
Pairing items from two groups so the total cost is lowest and nothing is used twice. Solved here with the Hungarian algorithm.
Evidence ID
The ID we cite as proof: a file_id, an activity_id or an audit_id.
Trace
A detailed diary of how the program reached each answer, so a human can review it.
SQL snapshot
A text dump of database tables at one moment. We load it into SQLite (a tiny built-in database) to query it.
